# 图片存储方案：Base64 vs 文件系统 vs 对象存储

## 可行性分析 + 行业最佳实践

**日期：** 2026-06-22
**当前存储架构：** 文件系统 + SQLite 路径引用

---

## 一、当前架构

```
运行时图片存放：
  output/<task_id>/pages/          ← PDF 渲染页 (200KB–1.3MB/张)
  output/<task_id>/annotated_pages/← YOLO 标注图
  db_data/kb_previews/<batch>/     ← 知识库预览图 (310–520KB/张)
  uploads/                         ← 上传原始文件

数据库：
  SQLite db_data/2d-v.db (224KB)
  ├── vectors_v2.vector BLOB       ← 文本嵌入向量 (非图片)
  ├── vectors_v2.content TEXT      ← 工艺文本
  └── preview_image_urls TEXT      ← 图片路径引用 (非二进制)

前端访问：
  /api/result/<task_id>/asset/<filename>
      → 读取磁盘文件 → 返回 PNG
```

> 当前总图片量：约 **21MB**（开发环境），实际生产运行后会显著增长。

## 二、可行性分析：Base64 存数据库

### 技术可行性：✅ 可以，但不应该

**SQLite 存储能力：**

| 参数 | 值 |
|------|-----|
| 单行 BLOB 最大 | 2GB（默认 1GB） |
| 数据库最大 | 281TB |
| Base64 膨胀 | +33% 体积 |

一张 A4 图纸页面（200DPI PNG ~1.3MB）→ base64 ~1.7MB。20 张图纸就是 34MB。加上 PDF 页面、标注图，一个任务轻松 20-50MB base64 数据。

### 性能影响

```
当前（文件系统）：            Base64 存 SQLite：
  读图：open() → send_file    读图：SELECT BLOB → decode → send
  延迟：~1ms                  延迟：~10-50ms
  DB 大小：224KB              DB 大小：50MB+（而且持续增长）
  备份：文件独立              备份：每次备份整个臃肿的 DB
  并发：OS 文件缓存           并发：SQLite 单写锁，读图阻塞写入
```

### 致命问题

| 问题 | 说 明 |
|------|------|
| **SQLite 单写锁** | 多个用户同时上传时，读写图片会互相阻塞。SQLite 的 WAL 模式只是读不阻塞读，写仍然串行 |
| **数据库膨胀** | 生产环境 100 张图纸 → DB 瞬间 200MB。`VACUUM` 无效（图片 BLOB 不会被清理） |
| **备份灾难** | 现在备份 DB 只需 224KB。存 base64 后每次备份几百 MB |
| **API 响应慢** | 每个图片请求 = 1 次 SQL 查询 + base64 解码。SSE 流式输出时尤其明显 |
| **缓存失效** | OS 文件系统缓存自动工作。SQLite BLOB 无系统级缓存，全靠应用层 |

## 三、行业最佳实践

### 3.1 制造业 CAPP/PLM 系统

| 系统 | 存储方案 |
|------|----------|
| Siemens Teamcenter | 文件系统 (volume) + Oracle 路径引用 |
| Dassault DELMIA | 文件系统 + ENOVIA 数据库指针 |
| PTC Windchill | 电子仓库 (文件系统/对象存储) + DB 引用 |
| 开目 CAPP/MPM | 文件系统 + SQL Server 路径 |
| 华天软件 CAPP | 对象存储 + DB URL |

**结论：** 没有一家成熟的工业软件把图纸/图片存成 base64 到数据库。

### 3.2 Web 应用行业通用做法

```
小图标 / 缩略图 (< 50KB):
  ✅ base64 inline (减少 HTTP 请求)
  ✅ 或 CSS Sprite

中等图片 (50KB – 5MB):
  ⭐ 文件系统 + DB 路径 ← 你们当前的方案
  ⭐ 对象存储 (S3/MinIO) + DB URL  ← 生产环境推荐

大文件 / 视频 (> 5MB):
  ⭐ 对象存储 + CDN
  ❌ 绝不存数据库
```

### 3.3 什么时候用 Base64 存 DB

| 场景 | 推荐度 |
|------|--------|
| 用户头像 / 小图标 (< 30KB) | 🟢 可以 |
| 缩略图缓存 | 🟢 可以（加速列表页） |
| PDF 页面预览图（200KB+） | 🔴 不推荐 |
| 图纸原图（1MB+） | 🔴 绝不 |
| 注释/标注覆盖图 | 🔴 不推荐 |

## 五、推荐方案

### 近期（当前阶段）：保持现状，小幅优化

```
为什么不变：
  - 当前 21MB 图片完全可控
  - 文件系统读写性能最优
  - SQLite 专做元数据和向量检索，各司其职
  - 没有任何生产问题需要切换到 base64

可选优化：
  ✅ 统一图片路径管理（现在 output/ + db_data/ + uploads/ 三处分散）
  ✅ 增加图片清理策略（过期任务自动删 output/）
  ✅ 缩略图生成（前端列表页加载快）
```

### 中期（生产化后）：引入 MinIO

```
架构：
  MinIO/S3  ← 图片/PDF/模型
  PostgreSQL ← 元数据 + 向量
  SQLite    ← 保留为离线/桌面版

图片访问：
  前端 → Nginx → /api/asset/... → Flask → MinIO presigned URL
  或 前端 → Nginx → 直接代理 MinIO（更快）
```

### 长期：如果坚持要"数据库管理"

> 用 PostgreSQL 的 BYTEA + TOAST + 独立表空间。这不是 SQLite 能承担的。

## 六、结论

| 问题 | 答案 |
|------|------|
| Base64 存 SQLite 能不能做？ | 技术上能，工程上不该做 |
| 当前方案对吗？ | 对，这是制造业软件的行业标准做法 |
| 需要改吗？ | **不需要**。当前架构正确，没有必须改的理由 |
| 什么情况下值得改？ | ① 多机部署需要共享存储 → 上 MinIO；② 需要从多个服务读取 → 上对象存储。**都不是因为"图片在数据库里更好"** |

**一句话：你们现在的做法（文件系统 + DB 路径）就是正确答案。不要改成 base64 存 SQLite，那是倒退。**
