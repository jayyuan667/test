# Role Architecture Design

## Goal

在不重做整站导航结构的前提下，明确 Web 端三类角色的层级关系、后台边界与业务页裁切方式：

- `user`：只使用，不治理
- `enterprise_admin`：企业运营管理员，不是半个平台管理员
- `super_admin`：平台治理者

本次设计的目标不是增加更多页面，而是让：

- 权限边界更清楚
- 业务页更克制
- 管理后台更分层
- 动效只服务理解和反馈，不增加复杂度

## Accepted Direction

### 1. Stable Navigation

主导航骨架保持稳定，不按角色改变整体站点结构。

所有角色都可见：

- `工艺入库`
- `工艺生成`
- `历史记录`
- `知识库浏览`
- `个人中心`

只有 `enterprise_admin` 和 `super_admin` 可见：

- `管理后台`

角色差异主要通过以下方式表达：

- 是否显示后台入口
- 页面内模块裁切
- 页面内动作权限差异
- 页面文案语义差异

### 2. Role Definitions

#### `user`

定位：

- 执行业务任务
- 查看自己的结果、历史与可访问知识

原则：

- 不接触成员治理、企业授权、平台配额
- 不承担治理复杂度
- AI 界面只强调结果、建议、下一步动作

#### `enterprise_admin`

定位：

- 负责本企业的运营治理

原则：

- 只管理本企业的人、配额、授权状态
- 不是平台管理员
- 不出现跨企业治理或平台总览语义

#### `super_admin`

定位：

- 负责平台级治理

原则：

- 承担企业治理、用户治理、平台配额总览
- 只有这一层出现平台级复杂度

### 3. Admin Console Split

后台只拆成两种，不扩成多层后台树。

#### Enterprise Admin Console

页面命名建议：

- `企业管理台` 或 `企业运营台`

模块仅保留：

- `成员`
- `配额`
- `授权状态`

禁止出现：

- 企业列表治理
- 跨企业用户分配
- 平台总配额
- 平台级统计语言

#### Super Admin Console

页面命名建议：

- `系统管理` 或 `平台管理`

模块保留：

- `企业管理`
- `用户管理`
- `配额概览`

后续如需新增模块，也应保持平台治理语义，不污染企业管理台。

### 4. Business Page Scoping

同一业务页继续复用，但按角色裁切模块和动作。

#### `工艺入库`

`user`

- 默认写入自己的可用范围
- 尽量不暴露复杂目标库选择
- 强调上传、结果、写入成功反馈

`enterprise_admin`

- 增加一个轻量范围切换：`个人 / 企业`
- 仍然保持业务页视角，不转成治理页

`super_admin`

- 才出现公共基线或平台级写入目标

#### `知识库浏览`

`user`

- 只强调查询、复用、快照、来源
- 弱化“库治理”感

`enterprise_admin`

- 增加企业范围筛选
- 增加少量企业内运营动作
- 仍保持为业务页，不做后台化

`super_admin`

- 才允许出现跨企业 / 平台级范围与治理动作

#### `工艺生成`

三类角色都保留相同主流程。

差异只体现在辅助信息：

- `user`：结果、建议、下一步
- `enterprise_admin`：额外可见企业复用与入库影响
- `super_admin`：额外可见平台级质量或治理视角

生成页本身不应因角色差异而显著复杂化。

#### `历史记录`

保持偏业务执行页的稳定性。

- `user`：看自己的历史与输出
- `enterprise_admin` / `super_admin`：如需扩展，也应优先加筛选能力，而不是增加治理面板

#### `个人中心`

所有角色统一收口：

- 账户信息
- 企业归属
- 个人配额
- 授权期限
- 修改密码

这里不承载任何治理动作。

## Motion Principles

整体原则：`less is more`

管理页与业务页不追求“展示感”，动效只承担三件事：

1. 页面级切换反馈
2. 操作级反馈
3. 关键节点聚焦

### Allowed Motion

- 页面切换时轻微淡入 / 上浮
- 后台 tab 切换的轻量过渡
- 范围切换（个人 / 企业 / 平台）时的内容过渡
- 上传、生成、保存、确认等关键动作的短反馈
- 权限受限状态的轻提示

### Avoid

- 后台表格普遍漂浮
- 大量 pulse、数字翻滚、发光描边
- 全局卡片统一做展示型动画
- 为了“科技感”增加持续性动效噪声

推荐节奏：

- 管理页：静 80%，动 20%
- AI / 生成页：静 65%，动 35%
- 认证入口可保留为全站表现力最强区域

## Copy Principles

角色分层不仅是权限问题，也是文案问题。

要求：

- `enterprise_admin` 页面中不出现“平台”“全部企业”“跨企业治理”等词
- `super_admin` 页面中明确使用平台级语义
- `user` 页面中尽量不出现治理语言

前端需要通过标题、筛选命名、按钮文案和空状态文案，把角色边界说清楚。

## Implementation Order

建议实施顺序：

1. `管理后台`
2. `知识库浏览`
3. `工艺入库`
4. `个人中心`
5. `工艺生成 / 历史记录` 仅做轻裁切

原因：

- 角色边界最先在后台失真
- 浏览与入库最容易混淆“业务”和“治理”
- 生成与历史应尽量保持稳定

## Final Constraints (2026-06-25 Rollout)

以下约束在实施中已确认并锁定，后续变更需通过新的设计文档：

### User Classification

- `user` 继续区分**未分配企业**（enterprise_id = null）与**已分配企业**（enterprise_id != null）
- 未分配企业 users 不得获得业务能力入口（工艺生成、工艺入库、历史记录、知识库浏览均不可见）

### Scope Mapping

- 当前范围映射：**个人 = private library**，**平台 = public library**
- 企业范围（enterprise scope）仍为**前端表达层**，不新增后端 scope 契约
- 企业范围仅通过界面引导文案体现（如 ZIP 入库页的 `#zip-target-library` 提示），不生成独立的后端 `library_scope` 枚举值

### Route Model

- 前端路由模型保持 **useState 驱动**，不引入 react-router
- PageId 枚举值在 `types/index.ts` 中管理

### Auth Model

- 现有认证模型（AuthContext + JWT HttpOnly Cookie）不做结构性变更
- 角色信息通过 `/api/auth/me` 返回的 `user.role` 字段传递

### Copy Constraints

- `enterprise_admin` 页面/组件中禁止出现"平台""全部企业""跨企业治理"等词语
- `super_admin` 页面/组件中明确使用平台治理语言（"平台管理""平台配额概览""企业管理"）
- `user` 页面中不出现治理语言

### Motion Budget

- 管理页：静 80%，动 20%
- AI/生成页：静 65%，动 35%
- 动效仅服务三件事：页面切换反馈、操作反馈、关键节点聚焦

## Success Criteria

完成后应满足：

- 三类角色关系在前端可以被一眼理解
- 普通用户不再看到不必要的治理复杂度
- 企业管理员被明确限制在企业运营范围内
- 超级管理员承担平台复杂度
- 同一业务页在不同角色下仍属于同一产品语言
- 动效比现在更有规则，但整体更克制
